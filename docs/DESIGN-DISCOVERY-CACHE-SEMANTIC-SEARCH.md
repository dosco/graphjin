# Coordinated Discovery Cache and Semantic Catalog Search

> **Status: implemented.** The service implementation is in
> `serv/discovery_generations.go`, `serv/semantic_index.go`,
> `serv/semantic_documents.go`, and `serv/semantic_query.go`. Core remains free
> of Ax and accepts generic catalog candidate hints.

## Goals

- Start GraphJin Service from a complete, validated schema snapshot instead of
  repeating large database discovery on every warm start.
- Coordinate discovery and document embedding once across horizontally scaled
  replicas without putting schema metadata or vectors in Redis.
- Improve catalog recall for business-language searches while keeping exact
  identifiers, visibility policy, filters, and real metadata relationships
  authoritative.
- Bound vector count for very wide schemas and incrementally reuse embeddings
  when catalog documents are unchanged.
- Preserve lexical catalog availability through provider, Redis, index, or
  dimension failures.

## Non-goals

- Vector database or approximate-nearest-neighbor graph.
- One vector per column.
- Redis vector or schema storage.
- Persisted query embeddings.
- Vector-inferred joins.
- A behavior change for direct embedded users of `core.NewGraphJin`.

## Ownership boundary

The service owns Ax, Redis coordination, filesystem generations, and query
embedding calls. Core owns schema reconstruction, catalog visibility and
filtering, lexical postings, generic candidate fusion, sorting, and pagination.

The service sends `CatalogCandidateHint` values to
`CatalogSnapshot.QueryResultWithHints`. Core does not import Ax and the existing
`CatalogSnapshot.QueryResult` API remains unchanged.

## Filesystem layout

The configured `discovery_cache.path` contains immutable data:

```text
.graphjin/discovery/
  generations/<discovery-generation-id>/
    <source>.schema.json
    <source>.sql
    manifest.json
  activations/<discovery-generation-id>.json
  semantic/<embedding-fingerprint>/
    generations/<semantic-generation-id>/
      documents.json
      vectors.f32
      manifest.json
    activations/<semantic-generation-id>.json
```

The exact source filenames are generated by core helpers. Discovery snapshots
contain full `DBInfo` metadata captured immediately after live introspection and
before config-derived schema augmentation. DDL remains diagnostic and a legacy
fallback; it is not the full-fidelity cache format.

Files are written before their manifest. Loaders verify format version,
generation identity, fingerprint, size, SHA-256 checksum, source-to-snapshot
coverage, vector count, and vector offsets. Activation receipts are written
only for successfully activated generations. A filesystem implementation that
does not support deletion safely retains older immutable generations.

## Discovery generation lifecycle

1. Derive a secret-free fingerprint from schema-affecting core/database
   configuration. Credentials, users, raw connection query parameters, keys,
   tokens, certificates, and PEM data are redacted.
2. Create a temporary live-discovered core with its per-process watcher
   disabled. Live introspection writes full schema snapshots and optional DDL.
3. Build the live catalog and collect its source/catalog revisions.
4. Create a second temporary cache-first core from those snapshots.
5. Require the cache-loaded catalog revision to equal the live catalog
   revision.
6. Write the discovery manifest last.
7. Activate under a local lock or fenced Redis lease, then write the durable
   activation receipt.
8. Atomically reload the stable service `GraphJin` pointer from the activated
   snapshot directory and notify semantic indexing of the catalog change.

If source and catalog revisions are unchanged, the temporary candidate is not
activated as a new generation.

## Coordination modes

### Single process

An absent `redis.url` is a supported operating mode. Process-local discovery
and semantic mutexes ensure only one builder runs inside the service process.
Durable generations still live on the configured filesystem, so warm startup
and incremental semantic reuse work normally.

### Horizontal deployment

Multiple replicas require Redis plus a shared read-after-write filesystem.
Discovery and semantic scopes have separate leases, fencing counters, active
generation keys, status, dirty counters, and PubSub event channels. The
discovery Redis prefix also includes the config fingerprint, preventing
schema-affecting configurations from sharing an activation namespace.

Leases are renewed during long builds. Activation is a Redis script that
requires the current lease value, advances the active ID, stores status, and
publishes the generation. A stale writer whose lease was lost cannot activate.

Redis contains coordination state only. Followers load the activated generation
from the shared filesystem and never receive schema or vector payloads over
PubSub.

## Startup and failure matrix

| State | Result |
| --- | --- |
| No Redis configured, no cache | Local discovery builds and activates the first generation. |
| No Redis configured, valid cache | Start cache-first; local background refresh is enabled. |
| Redis available, no cache | One fenced builder discovers; followers subscribe and poll up to `startup_wait`. |
| Redis available, valid cache | Start immediately; one lease holder refreshes in the background. |
| Redis unavailable, valid cache | Start stale/degraded from filesystem and suspend coordinated rebuilding. |
| Redis unavailable, no cache | Fail after `startup_wait` to prevent a discovery stampede. |
| Redis active ID missing on one replica | Keep the prior generation, report degraded status, and do not rebuild locally. |
| Corrupt or partial generation | Ignore it; only a checksum-valid activated generation can load. |

Explicit reload and schema-affecting config changes use the same coordinated
path. They wait for activation instead of running an independent reload.

## Semantic document model

`buildSemanticDocuments` creates deterministic documents from the shared base
catalog and metadata snapshot:

- `table_identity`: qualified name, table type, and available comment.
- `column_facet`: identifiers, measures, time, categorical/status,
  text/search, or other, split into chunks of 64 columns. Each member includes
  name, type, available comment, and key/index/null/array flags.
- `relationship_neighborhood`: the table's real one-hop tables and exact
  foreign-key columns.
- `concept`: safe shared help, capability, recipe, workflow, fragment,
  saved-query, and other non-schema cards.

The canonical text is hashed with the document format version. Persisted
`documents.json` keeps only the hash, kind, target card IDs, member column IDs,
and vector offset. `vectors.f32` stores normalized little-endian float32 data.

Sensitive cards and caller-owned artifacts are excluded. Config values,
evidence payloads, examples containing values, query/workflow bodies, and
caller-owned content are not semantic inputs.

For a 1,000-table by 300-column schema, at most ten facet chunks plus identity
and neighborhood documents are created per table: approximately 12,000 vectors
and 6 MB of raw 128-dimension data.

## Semantic generation lifecycle

The embedding fingerprint includes normalized provider, model, base URL,
dimension preset, and semantic document format version. The manifest also
records the actual dimension and catalog revision.

Under the same fingerprint, existing vectors are indexed by document hash and
reused. Only missing hashes are embedded; documents absent from the new build
are dropped. A fingerprint change prevents index reuse and causes a complete
rebuild. A runtime dimension mismatch invalidates the active index, clears the
query cache, and requests a full rebuild.

Embedding work uses batches of 64 and two workers. Only the local single-node
builder or semantic Redis lease holder calls the document embedding provider.
A compatible older index can remain active while the new catalog revision is
being built. A different embedding fingerprint is never served.

## Hybrid retrieval

1. Core's token postings generate exact lexical candidates. Trigram postings
   are used as typo fallback instead of unioning a broad candidate set.
2. If the top lexical result is an exact identifier, return lexical results and
   skip query embedding.
3. Otherwise, embed the query under a two-second context. Query vectors use a
   1,024-entry, ten-minute per-replica LRU and are never persisted.
4. Exact-scan normalized document vectors using a dot product (cosine score).
5. Sort scores, exclude the top eight when calculating background p99, require
   `score >= max(0.25, p99 + 0.02)`, retain only hits within `0.10` of the best,
   and cap at 64 documents.
6. Map table and facet documents to visible cards. Explicit column queries rank
   the facet's member columns using lexical relevance and deterministic column
   salience.
7. Select at most four distinct table endpoints. Run deterministic BFS over
   caller-visible catalog relationship cards and return at most two shortest
   paths of three edges or fewer, including real intermediate tables and
   relationship cards.
8. Core fuses candidates with reciprocal rank fusion (`k=60`): lexical weight
   `1.0`, semantic weight `0.7`, and graph-path weight `0.5`. Exact identifiers
   remain pinned.
9. Core reapplies `where`, shorthand filters, visibility, `order_by`, limit,
   and offset to the hybrid union. Explicit non-relevance ordering sorts the
   union by the requested fields.

`explain: true` reports lexical, semantic table/facet/concept, and deterministic
relationship-path provenance. Embedding errors, invalid dimensions, or query
timeouts return the lexical result rather than failing `query_catalog`.

## Agent-only adaptive coverage

The service passes a semantic catalog-search feature profile into the built-in
agent only after the semantic subsystem is constructed. This conditionally
extends `runtime.usageInstructions` and the internal `query_catalog` schema;
the public MCP schema, YAML configuration, direct-core API, and lexical-only
agent remain unchanged. The mandatory full-instruction seed also remains
unchanged.

The internal `searches` argument accepts two or three unique UTF-8 phrases,
each at most 512 bytes. It is mutually exclusive with `search`, `id`, `ids`,
and `order_by`, forces explanations, and may be used once per agent run. The
agent is told to use it only for missing multi-entity endpoints or paths,
missing column coverage, empty results, or material ambiguity.

Coverage retrieval first runs lexical search for every phrase and removes
exact identifiers from the embedding work. It reads query-vector cache hits,
sends every miss in one Ax embedding request under the existing two-second
deadline, validates every dimension, and falls back to lexical results for the
whole batch on provider failure. Exact scans and hybrid ranking then run
sequentially per phrase. Cross-phrase fusion uses equal-weight RRF (`k=60`),
never cosine-score addition: exact identifiers are pinned, one distinct visible
anchor is reserved per phrase, and remaining candidates are rank-fused.

The fused visible table endpoints feed the same caller-visible relationship
BFS. Returned path cards pass through core filters before they reach the agent.
The response retains per-phrase IDs and explanations plus agent-only metadata:
retrieval mode, exact-match status, semantic candidate count, visible table
endpoints, relationship-path count, and lexical-fallback state.

The fused result also supplies `next.args.ids`, a bounded, visibility-filtered
detail handoff containing endpoint tables and real relationship-path cards.
The agent uses it directly before answering; it does not need to reconstruct
IDs from phrase groups. Repeated coverage remains an actionable protocol error,
and empty `ids` arrays are rejected rather than treated as broad catalog scans.

The end-to-end discovery-quality smoke is:

```bash
examples/coffee-roastery/scripts/semantic-smoke.sh
```

It starts the real coffee-roastery service and MCP transport first with lexical
search and then with semantic search, compares ranks for business-language
queries, checks a real foreign-key path, checks an unrelated-query control,
and restarts from the same isolated filesystem generation to prove warm
startup performs no document embeddings. The default deterministic Ax-
compatible endpoint makes this repeatable in CI. It also runs the deterministic
agent-only service-runtime coverage assertion. Add `--agent` to drive the real
REST agent and Ax/Goja runtime through one private three-phrase coverage call,
cache-aware batched embedding, returned-card detail inspection, and catalog-only
relationship evidence. `--live` runs the retrieval acceptance cases against the
configured provider and embedding model; live-model agent evaluation remains a
separate optional quality check.
